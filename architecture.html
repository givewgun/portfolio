Case Study 01 35 Public ADRs Distributed Systems · NATS

Legion — Leaderless Multi-Agent Consensus Engine

Reproducible multi-LLM signal consensus over a NATS message bus with no prime decider, statistical anti-herding & correlation guards, crash-recoverable state replay, and an outbox-decoupled broker execution pipeline.

ARCHITECTURE.md ↗ Browse 35 ADRs ↗
Problem & Constraints

Single-LLM trade opinions hallucinate and shift between runs. Legion coordinates 4 specialized LLM voters (technical, news, social, contrarian) plus a deterministic risk node on a single Oracle ARM64 VM with local Ollama inference — requiring deterministic, reproducible consensus with no single point of decision and zero chance of a slow broker blocking signal emission.

Selected ADRs (Verified on GitHub)
ADR-0001BFT-flavored leaderless weighted aggregation (κ quorum + θ_v dispersion)↗ ADR-0015Redundancy-discounted quorum via Pearson correlation mass↗ ADR-0016Anti-herding guard requiring round-1 backing on later-round consensus↗ ADR-0024Crash-recoverable emitter with pending-vote replay↗ ADR-0035Transactional outbox + duplicate-cOID idempotent broker execution↗
Rejected Alternatives
  • Chairman / arbiter LLM: Rejected — creates a non-reproducible single point of failure where one prompt swing overrides the panel.
  • Plain weighted average: Rejected — a high-conviction outlier drags the mean with no explicit gate for "we disagree too much to act."
  • Direct broker calls in emitter: Rejected — broker auth/network stalls would block cycle finalization and Telegram delivery; solved via legion.order_intents outbox.
Failure Modes & Mitigations
  • Echo-chamber voting: Pairwise Pearson correlation discounts co-moving agents (mass_i = 1 + Σ max(0, corr)) so correlated echoes collapse toward 1 independent voice.
  • Mid-round process crash: Emitter persists votes before aggregating; on restart it rebuilds buffers, restores round-1 priors, and replays any stranded transition.
  • Duplicate orders on retry: Client Order ID (cOID) equals the intent ID, relying on broker duplicate-cOID rejection for safe crash recovery.
Case Study 02 15 Public ADRs Zero Deps · MCP · npm

tandem — Cross-Model Agent Orchestration

An open-source CLI and hand-rolled MCP server pairing Claude Code with Google Antigravity (Gemini) on flat-rate subscriptions — with zero API keys, zero runtime dependencies, and live 5h/weekly quota routing.

ARCHITECTURE.md ↗ Browse 15 ADRs ↗
Problem & Constraints

Developers already pay for flat-rate Claude and Gemini subscriptions, yet cross-model tooling usually demands paid API keys, loses each CLI's native tools, and lets an agent rubber-stamp its own bugs. tandem had to run identically on Windows, macOS, and Linux with zero runtime dependencies, zero stored API keys, and truthful plan-window metering.

Selected ADRs (Verified on GitHub)
ADR-0001Node ESM with zero runtime dependencies & argv-only process spawning↗ ADR-0002Drive headless agent CLIs, not raw APIs (subscriptions, no keys)↗ ADR-0007Hand-rolled MCP server exposing only the partner model family↗ ADR-0009Route on live 5-hour & weekly plan windows, not fake USD budgets↗ ADR-0011Native transcript reading + Stop hooks with TANDEM_MANAGED dedupe↗
Rejected Alternatives
  • Model REST APIs: Rejected — double-bills users on top of existing subscriptions and strips away native codebase tools.
  • Dollar-based weekly limits: Rejected — flat-rate plans throttle on rolling 5h/weekly utilization windows, not API dollars.
  • Shell-string process invocation: Rejected — Windows quoting and injection hazards; src/proc.js spawns argv arrays with explicit timeout + tree kill.
Failure Modes & Verified Outcomes
  • Self-review blind spots: Asymmetric MCP exposure makes self-review structurally impossible; a cold cross-model review caught 5 real release bugs, including a DNS-rebinding hole in the local dashboard.
  • Large prompt truncation on Windows: Prompts >24k chars switch from argv to stream-json stdin without writing temp files to disk (ADR-0004).
  • Double-counted token telemetry: Managed child sessions carry TANDEM_MANAGED so Stop hooks skip them while still capturing direct interactive work.
Case Study 03 5 Public ADRs AI Infra · Split Control Plane

local-llm-server — Self-Hosted AI Inference Gateway

Production-grade OpenAI-compatible LLM API on a single home GPU with vLLM continuous batching, zero-downtime Ollama fallback during model swaps, multi-tenant LiteLLM virtual keys, Cloudflare Tunnel path-allowlisted ingress, and a Tailscale-only admin & observability plane.

architecture.md ↗ security.md ↗
Problem & Constraints

Exposing a single home GPU (16 GB VRAM behind consumer NAT/CGNAT) as a multi-tenant OpenAI-compatible API requires high concurrent throughput, zero open router ports, strict isolation between public inference and key-management admin routes, and clean model swaps without breaking client configs.

Selected ADRs (Verified on GitHub)
ADR-0001vLLM primary (PagedAttention + batching) with Ollama fallback↗ ADR-0002LiteLLM + Postgres virtual keys, RPM/TPM caps & stable aliases↗ ADR-0003Git-managed Cloudflare Tunnel with strict path allowlist↗ ADR-0004Admin UI, key minting & Grafana isolated on Tailscale tailnet↗ ADR-0005Docker Compose profiles + pinned tags + single llmctl CLI↗
Rejected Alternatives
  • Direct vLLM behind nginx + static key: Rejected — no per-client rate caps, no usage accounting, and clients break on every model swap.
  • Router port-forward + Caddy/Let's Encrypt: Rejected — exposes home IP, breaks under CGNAT, and leaves DDoS protection on the host.
  • Tailscale Funnel for public traffic: Rejected — locked to *.ts.net with no WAF or custom domain path filtering.
Security & Operational Controls
  • Two-layer admin isolation: Public tunnel only routes ^/(v1/.*|health/liveliness)$ (everything else including /metrics and admin UI returns 404) and master key never leaves the host.
  • Zero prompt leakage in logs: turn_off_message_logging: true keeps spend/usage metadata while never persisting raw prompts or completions.
  • Zero-downtime model switching: Clients target local-chat; while vLLM reloads a new YAML preset, LiteLLM transparently serves requests from Ollama.
Case Study 04 ESP-IDF C · Threat Model Zero-Trust IoT · Pentested

esp32-wol — Zero-Inbound-Port IoT & Remote Wake Security

Hardware-to-cloud remote workstation boot & AI-coding control plane: native ESP-IDF C firmware over outbound-only TLS MQTT, dual-verified Cloudflare Access JWTs, HMAC-SHA256 signed commands with replay protection, and a written pentest.

security.md ↗ MQTT Protocol ↗ Pentest Report ↗
Problem & Threat Model

Waking a home workstation remotely and spawning autonomous coding sessions (bypassPermissions) is remote code execution by design. The system had to work with zero home-router port forwarding, tolerate a potentially compromised cloud MQTT broker, and fail closed at every boundary.

Security & Protocol Specs (On GitHub)
THREATFail-closed threat model: Access JWT + HMAC-SHA256 + replay guards↗ PROTOTopic schema, QoS 1 non-retained commands, LWT & clean-session rules↗ ESP-IDFNative C firmware on ESP-IDF v6.1 with TLS 8883 & WoL broadcast↗ PENTESTDocumented security pentest against the PC dashboard & agent↗
Rejected Alternatives
  • Trusting the MQTT broker as the auth boundary: Rejected — broker credentials live on phone + ESP32; privileged session commands require a separate PC_CMD_SECRET HMAC-SHA256 signature only the dashboard and PC share.
  • Cloudflare Access edge-only check: Rejected — container also validates RS256 Access JWTs via Cloudflare JWKS on every /api route so direct container reachability still fails closed.
  • Retained MQTT commands / persistent sessions: Rejected — would cause a stale shutdown sent while offline to immediately kill the PC on next wake.
Defense-in-Depth Mitigations
  • Replay attacks: Every signed command carries a unique id (cached 120s) and timestamp ts checked within ±60s of PC clock and strictly after agent boot time.
  • Spoofed status replies: PC replies are also HMAC-signed; the dashboard drops unsigned or tampered replies.
  • Path traversal & shell injection: Folder names must match a listed workspace subfolder (rejecting .., symlinks, junctions, hidden dirs) and spawn via argv lists with 4 KB payload caps.
Case Study 05 ARM64 · $0/mo Runtime Observability · Zero-Trust Ingress

Oculory — Three-Pillar Self-Hosted Observability

Unified Prometheus metrics, Loki logs, and Tempo distributed traces with end-to-end exemplar & trace_id correlation — running on an Oracle Always-Free ARM64 VM behind Cloudflare Tunnel and Access.

ARCHITECTURE.md ↗ METRICS.md ↗
Problem & Constraints

Running multiple services (GunVest, Legion, Horizon) on one Oracle Always-Free ARM64 VM meant tight RAM/disk budgets and zero appetite for SaaS observability bills. The goal: true three-pillar correlation (click a latency spike → slow trace → structured logs) with disk-bounded retention and zero exposed firewall ports.

Key Engineering Decisions
  • Single collector (Grafana Alloy): Replaced separate Promtail + OTel Collector containers with one agent handling Docker stdout JSON tailing and OTLP :4317/:4318 ingestion.
  • Custom docker-stats exporter: Built a lightweight in-repo exporter reading the Docker API directly after cAdvisor failed to register containers on the host's overlayfs driver.
  • Cross-bus trace stitching: Legion's NATS wrapper injects W3C traceparent into message headers so scheduler → agents → Ollama → emitter form a single distributed trace.
Rejected Alternatives
  • Promtail + separate OTel Collector: Rejected — extra memory footprint and duplicated service-discovery configs on a free-tier VM.
  • Head-based trace sampling: Rejected — drops rare errors; Alloy tail-sampling keeps 100% of errors and slow traces while sampling healthy traffic.
  • Public Grafana port + basic auth: Rejected — every service binds to 127.0.0.1 only; Grafana is gated strictly behind Cloudflare Tunnel + Access.
Operational Safeguards
  • Disk-bounded retention: Prometheus capped at 15d / 6 GB, Loki at 14d, Tempo at 7d so a log burst can never fill the root volume.
  • Standard RED contract: Every app emits http_request_duration_seconds with exemplars, powering service maps and alerts out of the box.
  • External visibility: Blackbox synthetic probes monitor public hostnames and TLS expiry from outside the app loop.
Case Study 06 6 Public ADRs Resilient Proxy · Same-Origin

Horizon — Resilient Space & Earth Telemetry

Single-process Fastify + React/CesiumJS dashboard aggregating 7+ volatile third-party space and weather APIs with single-flight caching, last-known-good stale fallback, and honest UI freshness badges.

ARCHITECTURE.md ↗ Read ADR-0004 ↗
Problem & Constraints

Public space and weather APIs rate-limit aggressively, time out, and break schemas. Naive dashboards either hammer upstreams per tab (thundering herd), leak API keys into the browser, or lie to users by silently showing hours-old data as "live."

Selected ADRs (Verified on GitHub)
ADR-0001Single-process Fastify + Vite SPA (no CORS, no frontend secrets)↗ ADR-0003Custom Canvas stereographic sky renderer over D3-Celestial↗ ADR-0004Single-flight TTL cache + last-known-good truthful degradation↗ ADR-0005Live channel scrape over quota-heavy YouTube Data API↗
Rejected Alternatives
  • Per-route ad-hoc caching: Rejected — guarantees inconsistent timeout/failure behavior across 7 upstream clients.
  • Silent stale-while-revalidate: Rejected — hides upstream outages from the operator; Horizon explicitly demotes the UI badge to SNAPSHOT · stale with ageMs.
  • Eager CesiumJS bundle: Rejected — heavy WebGL globe is code-split behind React.lazy + Suspense so initial load stays fast.
Failure Modes & Mitigations
  • Cache-miss thundering herd: Single-flight inflight map shares one upstream request across concurrent callers for the same key.
  • Upstream 429 / 8s timeout: Typed UpstreamError triggers lastGood(key) fallback before ever surfacing a panel failure.
  • Rate-limited geocoding: Nominatim client enforces a ≥1 req/s throttle server-side to respect fair-use policy.
